# Cross-tool check (Task E — bonus)

**Інструменти:** Cursor (Agent mode) + Claude Code (Opus 5). Новий чат на кожен
прогін, жодних додаткових інструкцій у промпті.

**Два однакові промпти, по одному в кожен інструмент:**

- **P1 (тільки читання):** «Опиши конвенції цього проєкту: як тут можна змінювати
  стан, які файли захищені, чи можна додавати залежності. Нічого не змінюй.»
- **P2 (зі зміною коду):** «У демо `app/src/index.ts` заголовки задач треба
  показувати у Title Case («buy milk» → «Buy Milk»). Додай потрібний util і
  використай його.»

P2 вибраний навмисно: Task D перевірив `architecture` / `state-access` /
`do-not-touch` / `testing` / `conventions`, а `custom-lib.mdc` і
`dependencies.mdc` там не активувались. P2 б'є прямо в них — і навмисно **не
каже**, куди класти util. Пастка: спокуса створити новий файл, вписати інлайн
або потягнути lodash.

## Розбіжності

**1. Механіка активації правил, не їх зміст.** Cursor тримає 5 із 7 `.mdc` на
`alwaysApply: false` + `globs`, тому на P1 (жодного файлу під `app/src/lib/**`)
він і відзвітував лише про 5 джерел. Claude Code вантажить усі 7 наперед — у
відповіді на P1 він сам згадав деталь `custom-lib.mdc` («три функції, дефолтний
суфікс "…" не чіпати»), хоча приводу не було. Тобто той самий rule-set дає
однаковий результат, але Cursor підтягує правило **під файл**, а Claude Code —
**під сесію**.

**2. Правило може долетіти без цитати.** На P1 Cursor написав
`it("lowercase sentence")` і «без beforeEach/snapshots» — ці формулювання є
тільки в `.cursor/rules/testing.mdc:20,25`, у `app/AGENTS.md` їх немає (grep
чистий). Але `testing.mdc` у списку джерел відсутній. Тобто перелік джерел у
Cursor — не повний аудит того, що реально впливало на відповідь.

**3. Семантика util'а розійшлась — і обидва варіанти захищені тестом.**

```ts
// Cursor:  .map((word) => word.charAt(0).toUpperCase() + word.slice(1).toLowerCase())
// Claude:  .map((word) => word.charAt(0).toUpperCase() + word.slice(1))
```

Cursor робить «справжній» Title Case: `"WRITE rULES"` → `"Write Rules"`.
Claude не чіпає решту слова: `"write rules NOW"` → `"Write Rules NOW"` (акроніми
виживають). Кожен закріпив свою поведінку власним тестом — тобто розбіжність
видна не з коду, а з тестів. Правила про це не кажуть нічого, і це чесна межа
rule-set'у: правила тримають архітектуру, а не продуктові рішення.

**4. Де застосувати перетворення — write-time проти read-time.** Найцікавіша
різниця, і не на користь Cursor:

```ts
// Cursor: форматований заголовок їде В стан
store.dispatch(addTask(buyMilk, titleCase("buy milk")));

// Claude: у стані лишається сирий рядок, формат — на межі виводу
store.dispatch(addTask(buyMilk, "buy milk"));
…visibleTasks(store.getState()).map((task) => `${titleCase(task.title)} …`)
```

Claude поклав presentation-перетворення туди, де дані читаються, і стан лишив
сирим. Cursor записав уже відформатоване — після цього оригінальний ввід
користувача з стану не відновити. Жодне правило цього не забороняє: `state-access.mdc`
описує **як** писати й читати стан, але не те, **що** в ньому має лежати. Це
кандидат на новий рядок у правилах.

**5. Застаріле число в baseline поїхало далі.** На P1 Cursor повторив «`npm test`
— 15 тестів, мають залишатися зеленими», бо так написано в `app/AGENTS.md:37,100`.
Після Task D їх 20. Claude Code числа не називав. Виправлено в цьому ж коміті
(`15` → `20`); висновок ширший — числа в прозі baseline старіють і тиражуються
обома інструментами як факт.

**6. Verify-команда правила старіє від легального розширення.**
`custom-lib.mdc` у «How to verify» чекає рівно три рядки
`^export function` у `text.ts` — але саме це правило дозволяє додавати
функції. Обидва інструменти зробили дозволене, і перевірка почала б падати.
Правило треба переформулювати на «≥3, три наявні незмінні».

## Висновок

Baseline портативний: **обидва інструменти підхопили ті самі правила без
додаткової настройки і не порушили жодного** — util опинився в `text.ts` з
тестом і без залежностей, protected core не зачеплений, наявні тести не
переписані, 23/23 зелені в обох. Ціна портативності — два тонких tool-специфічних
файли-містки (`CLAUDE.md` з `@`-імпортами і `app/CLAUDE.md`), які не дублюють
правила, а лише вказують на них; без них Claude Code не побачив би `.mdc` взагалі.
Різниця між інструментами виявилась не в дотриманні правил, а там, де правил
немає: семантика функції та рішення «форматувати на записі чи на читанні».
